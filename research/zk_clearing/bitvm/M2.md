# M2: the optimistic BitVM2 graph on Bitcoin regtest

Run 2026-11-01. Everything below was executed and measured unless it says otherwise. The demo
keys and Groth16 setup are public, so **none of it is safe with real funds**; it is regtest only.

Same machine, verifier, patch, proof and node as [M1.md](M1.md): BitVM `c620dbf` with
`patches/0001-bitvm-18-public-inputs.patch`, Bitcoin Core v31.1.0 with default policy apart from
`-blockmaxweight=4000000`.

## Headline

**The honest unchallenged batch costs 897 vB on chain: a 197 vB kickoff and a 700 vB payout.
M1 cost 423,361 vB for the same batch, 472 times more.** At 2 sat/vB that is 1,794 sats instead
of 846,722. The roadmap's gate (the honest path far below M1's 423 kvB) is met.

| Path (vbytes on chain, excluding escrow, bond and reserve funding) | M2 | M1 |
|---|---|---|
| **Honest, unchallenged:** kickoff + payout_unchallenged | **897** | 423,361 (M1 always asserts) |
| Honest, challenged: kickoff + challenge + assert chain + payout_asserted | 423,708 | — |
| Tampered and challenged: kickoff + challenge + assert chain + disprove(431) + 3 refunds | 662,428 | 662,018 |
| Challenged, operator silent: kickoff + challenge + timeout + 3 refunds | 978 | — |
| Challenged, assert incomplete: kickoff + challenge + assert_init + 5 commits + timeout + 3 refunds | 423,186 | — |
| Stall (no kickoff): 3 refunds | 390 | 414 |

The assert now costs on chain only when someone challenges, and the challenger pays for it. The
honest path's fixed cost is about 423 vB, plus 57.5 vB per escrow and 43 vB per payee output
(§4).

In every case the payouts pay byte-for-byte what the template says (the first seven outputs of
each mined payout were compared with it), and each slash leaves the poster exactly KB plus its
connector, less the 5,000,000-sat burn and the fee.

**A finding about the burn.** Core's mempool accepts the timeout (`testmempoolaccept` says
allowed), but `sendrawtransaction` refused it at first: "Unspendable output exceeds maximum
configured by user (maxburnamount)". That RPC refuses an OP_RETURN output carrying more than
`maxburnamount`, which defaults to 0. The check is local to the sending node's RPC, not relay
policy. Whoever posts a slash has to pass `maxburnamount` of at least 0.05 BTC. The harness now
does, and the silent run hit the refusal before that fix.

## Reproduce

M2 reuses M1's build and caches; see [M1.md](M1.md#reproduce) for steps 1 and 2.

```sh
# Builds convert, m1 and m2, and runs their 17 unit tests.
bash research/zk_clearing/bitvm/scripts/build.sh /root/zkc-m1
# A fresh bitcoind -regtest and every M2 scenario. Runs `zkc-m1 prepare` first if its cache is missing.
BITCOIN_BIN=/root/opt/bitcoin-31.1/bin bash research/zk_clearing/bitvm/scripts/run-m2.sh /root/zkc-m1
# The timeouts and the blocks each leaves to spare.
/root/zkc-m1/target/release/zkc-m2 timing
```

[`results/m2/`](results/m2/) holds one trace per scenario (every txid, vbyte and weight count,
mempool verdict, mined height, and the node's reason for every expected rejection), the timing
report and the run's timings.

The code is [`m2/src/graph.rs`](m2/src/graph.rs) (the graph) and [`m2/src/main.rs`](m2/src/main.rs)
(the scenarios). It compiles M1's chunked-verifier glue, RPC client, taproot helpers and payout
template from `m1/src` by path. The only change to M1's code is an additive constructor on its
taproot tree, for a tree whose internal key can also sign.

## 1. The graph

```
escrow[b]            P2TR(internal key: committee; leaf: T_refund CSV, <buyer b> CHECKSIG)
bond                 operator, 0.1 BTC, key path
reserve              operator, key path: pays for the assert chain if a challenge comes
kickoff              bond -> KC (330) + KA (330) + KB (the bond); each a committee key path
challenge            KC, committee SIGHASH_SINGLE|ANYONECANPAY: output 0 pays the operator the
                       assert chain's cost; the challenger adds its own inputs and change
payout_unchallenged  KC (nSequence T_challenge) + KA + KB + every escrow
                       -> the template's outputs + the bond back to the operator
assert_init          reserve -> 42 commit outputs C_j
commit[k]            C_j inputs, each through its leaf (Winternitz batch, then <operator> CHECKSIG)
                       -> connector D_k
assert_final         KA + D_0..D_4 -> A; P2TR(NUMS; 432 BitVM disprove leaves | 18 binding leaves
                       | payout: T_disprove CSV, <committee> CHECKSIG)
payout_asserted      A (payout leaf) + KB + every escrow -> the template's outputs + the bond back
disprove             KB (committee SIGHASH_SINGLE: output 0 burns 5,000,000) + A through a disprove
                       or binding leaf -> burn + the rest to whoever posts it
timeout              KB (committee SIGHASH_SINGLE: output 0 burns 5,000,000) + KA (committee
                       SIGHASH_NONE, nSequence T_assert) -> burn + the rest to whoever posts it
refund[b]            escrow[b] through its refund leaf, T_refund blocks after funding
```

**Committee.** One demo key stands in for BitVM2's n-of-n presigning committee. A MuSig2 aggregate
of n keys spends the same way on chain, so the sizes here hold for any n. Before the kickoff it
signs:

| Transaction | Inputs it signs | Sighash |
|---|---|---|
| payout_unchallenged | KC, KA, KB, 3 escrows | DEFAULT |
| challenge | KC | SINGLE\|ANYONECANPAY: KC and output 0 only |
| assert_final | KA (the operator signs D_0..D_4) | DEFAULT |
| payout_asserted | A's payout leaf, KB, 3 escrows | DEFAULT |
| disprove | KB | SINGLE: both inputs, output 0 (the burn); valid with any leaf of A |
| timeout | KB, KA | SINGLE on KB (output 0, the burn); NONE on KA (inputs only) |

That is 16 signatures, and one disprove signature covers all 450 disprove and binding leaves. It is
assumed to sign nothing else. With one key that is an assumption, not a guarantee.

**Why the graph has the shape it has.**

- *The challenge consumes only KC.* A challenge's txid is not known in advance, because the
  challenger adds its own inputs. No presigned transaction can therefore spend a challenge
  output. The challenge works by destroying KC, which payout_unchallenged needs.
- *KA carries the assert deadline.* KA is spent by assert_final, payout_unchallenged or timeout,
  and by nothing else. The timeout opens T_assert blocks after the kickoff. A challenged operator
  therefore has to get A confirmed by then, however much of the assert chain it posted. The
  `incomplete` scenario checks this.
  - The timeout needs no challenge. It also slashes an unchallenged operator whose payout nobody
    posts in the T_assert − T_challenge blocks before it opens.
  - payout_unchallenged is fully signed, so any party can post it.
- *The bond never moves until the end.* KB stays in the kickoff until a payout returns it or a
  slash burns half of it. In M1 the bond funded the assert chain; here the operator's reserve
  does, and the challenger reimburses it.
- *The challenger pays for the assert.* Output 0 of the challenge pays the operator 848,000 sats,
  the assert chain's cost at 2 sat/vB rounded up to 1,000 sats. Forcing the operator to post
  about 423 kvB is not free. A watcher challenges when the operator's π does not verify for the
  presigned statement, or when π was not published.
- *Every slash burns half the bond.* The committee's SIGHASH_SINGLE signature on KB fixes output 0
  as a 5,000,000-sat OP_RETURN. Output 1 onwards are not signed, so whoever posts the slash
  (the challenger, anyone, or a miner who replaces the output) takes the rest less the fee.
  An operator that challenges itself and slashes itself, or a miner it colludes with, gets back
  at most half the bond.
- *Committee outputs use the key path.* KC, KA, KB and the escrows' payout path are committee
  key-path spends (57.5 vB per input). Their relative timelocks are nSequence values the
  committee's signatures commit to, which BIP68 enforces. An OP_CSV leaf would add nothing,
  because the same key could sign without it. A keeps M1's NUMS internal key and its OP_CSV
  payout leaf, since its other leaves need no signature at all.
- *The assert chain is fixed before any assertion exists.* Segwit txids exclude witnesses. So
  assert_init, the commit transactions and assert_final have known txids, and the committee can
  presign assert_final and everything that spends A. The commit fees are sized for the largest
  witness any assertion can have (every Winternitz digit nonzero). Each real assertion then pays
  slightly more than 2 sat/vB.

## 2. Timeouts, set against each other

Write h_e for the escrows' confirmation height, h_k for the kickoff's and h_A for assert_final's.

| Timeout | Enforced by | Regtest (run) | Mainnet sketch (not run) |
|---|---|---|---|
| T_kickoff | policy: the operator kicks off by h_e + T_kickoff | 6 | 36 (6 h) |
| T_challenge | KC's nSequence in payout_unchallenged (BIP68) | 6 | 144 (1 day) |
| T_assert | KA's nSequence in timeout (BIP68), counted from the kickoff | 12 | 288 (2 days) |
| T_disprove | OP_CSV in A's payout leaf | 6 | 144 (1 day) |
| T_refund | OP_CSV in each escrow's refund leaf | 30 | 576 (4 days) |
| r | the reorg and inclusion margin every deadline must leave | 2 | 6 |

Each constraint below is the worst case for the party that has to act. Its slack must be at least
r. `zkc-m2 timing` computes these, and every scenario refuses to run if one falls below r.

| What must fit | Slack (blocks) | Regtest | Mainnet sketch |
|---|---|---|---|
| A challenge, mined in blocks h_k + 1 … h_k + T_challenge − 1 | T_challenge − 1 | 5 | 143 |
| The unchallenged payout, between h_k + T_challenge and the timeout at h_k + T_assert | T_assert − T_challenge | 6 | 144 |
| The assert chain after a challenge in the last possible block: assert_final lands at h_k + T_challenge − 1 + 3 at the earliest, and the timeout opens at h_k + T_assert | T_assert − T_challenge − 3 | 3 | 141 |
| A disprove, before payout_asserted opens at h_A + T_disprove | T_disprove | 6 | 144 |
| The latest payout_asserted, valid from h_e + T_kickoff + T_assert − 1 + T_disprove, before the first refund opens at h_e + T_refund | T_refund − (T_kickoff + T_assert − 1 + T_disprove) | 7 | 109 |

**Why the assert takes at least three blocks.** Core v31's mempool caps the size of a cluster
of related unconfirmed transactions (101 kvB by default), and each commit transaction is 53–92
kvB. In the challenged run, assert_init and commit[0] entered the mempool together. commit[1]
was then refused (`too-large-cluster`). So assert_init must confirm before the other commits
can relay, and assert_final, which spends all five, must wait for them. A miner could take the
whole chain directly in one block, but the timing does not assume one.

What the numbers cost the parties:

- **Latency.** An unchallenged batch settles T_challenge blocks after the kickoff.
- **Buyers' capital.** If the batch fails, buyers' funds are locked for T_refund.
- **Operator's capital.** The operator holds the bond for the whole graph, and the reserve unless
  the graph ends without a challenge.

The mainnet column is arithmetic on the constraints, not a recommendation from a run:

- The challenge and disprove windows assume watchers that are online daily.
- The disprove window must also cover getting a non-standard transaction (430 of the 432 leaves)
  to a miner.

## 3. Reorg and finality policy

Write r for the depth the parties treat as final. Nothing reorgs on regtest; r = 2 there is a
parameter of the slack checks, and no reorg was simulated. On mainnet, r = 6.

1. **Escrows and reserve before the kickoff.** The operator kicks off only when every
   escrow and the reserve have r confirmations.
   - Suppose an escrow vanished in a reorg after the kickoff and its coin were spent elsewhere. Then
     neither payout could ever be valid, and anyone could slash the honest operator at T_assert.
   - The same holds for the reserve, because assert_final is presigned against the txid of the
     assert_init that spends it.
   - T_kickoff counts from the escrows' confirmation, so T_kickoff ≥ r.
2. **The challenge.** A watcher posts its challenge as soon as it has checked π, or found π
   missing. It counts the challenge as done only once it is r deep before h_k + T_challenge.
   A reorg that drops a challenge from height h_k + T_challenge or later lets payout_unchallenged
   take KC instead.
3. **The assert.** The operator starts at the challenge's first confirmation and needs A r deep
   before h_k + T_assert. Nothing in the assert chain spends the challenge. So if the challenge
   is reorged out, the operator loses at most the assert fees, and only if no challenge is mined
   again to pay for them.
4. **The disprove.** A challenger needs its disprove r deep before h_A + T_disprove. For a
   non-standard leaf that includes the time to reach a miner.
5. **The payouts.**
   - payout_unchallenged needs to be r deep before h_k + T_assert, when the timeout opens.
   - Both payouts need to be r deep before h_e + T_refund, when the first refund opens.
   - Sellers treat a payout as final at r confirmations.
6. **Slashes and refunds.** Each opens only when a window closes. From then on it races any
   transaction that missed its deadline. The slack in §2 exists so that a party acting within r of
   its deadline never has to race.

## 4. What the honest batch costs on chain

The honest unchallenged path is the kickoff (1 key-path input, 3 P2TR outputs) and
payout_unchallenged (3 + E key-path inputs, P + 1 P2TR outputs), for E escrows and P template
outputs:

```
788 WU + 42 WU + 230 WU × (3 + E) + 172 WU × (P + 1)
  ≈ 423 vB + 57.5 vB per escrow + 43 vB per payee output
```

For the regtest batch (E = 3, P = 7) that is 897 vB, as measured. The roadmap estimated 1–2 kvB
plus 43 vB per payee output; the fixed part came in at under half a kvB.

## 6. Bond, burn and challenge: who pays what

At 2 sat/vB. Rows marked *est.* are arithmetic, not runs.

| Party | Unchallenged | Challenged, honest | Challenged, tampered | Challenged, silent |
|---|---|---|---|---|
| Operator | kickoff + payout fees; bond back | assert chain from its reserve, refunded by the challenge payment; bond back | loses the bond: half burned, half to the disprover | loses the bond: half burned, half to the slasher |
| Challenger | nothing | pays 848,424 sats (848,000 to the operator, 424 in fee) and gets nothing back | pays 848,424, gets 4,522,158 from the disprove: net +3,673,734 | pays 848,424; whoever posts the timeout gets 4,998,918 |
| Buyers and sellers | the template's outputs | the template's outputs, T_disprove later | refunds after T_refund | refunds after T_refund |

- **An honest challenged operator ends slightly ahead.** The challenge pays 848,000 sats; the
  assert chain draws 847,216 from the reserve. That leaves the operator 784 sats up, before the
  payout fee. This holds only at the fee rate the graph was signed at (§7).
- **The bond pays the challenger, so it must scale with the fee rate** (*est.*).
  - A challenger proving fraud pays two things, both proportional to the fee rate f: the
    challenge (about 424 kvB × f) and the disprove (up to about 990 kvB × f for leaf 425, the
    largest).
  - The disprove's fee comes out of its reward, KB − BURN. Breaking even therefore needs
    BOND − BURN ≥ f × 1.41 MvB.
  - With BOND − BURN = 5 M sats, that holds up to about 3.5 sat/vB for the largest leaf, and up to
    about 7.5 sat/vB for leaf 431, the one the tampered run used.
  - Which leaf a disprove needs depends on where the operator's assertion breaks, and a dishonest
    operator chooses part of that. Budgeting for the largest leaf is the safe assumption.
  - At 10 sat/vB the bond has to be about 0.28 BTC with a half burn.
- **The burn fraction trades two failure modes.**
  - A larger burn leaves less for an honest challenger.
  - A smaller burn lets a self-challenging operator, or a miner it colludes with, recover more of
    its bond.
  - Half is the run's choice, not a derived optimum.
- **A miner can take any slash reward.** Output 1 of a disprove or timeout is not signed, so the
  miner that includes it can redirect it. The burn caps what that is worth to an operator who is
  also a miner.

## 7. What M2 does not show

- **The fees are frozen at 2 sat/vB.**
  - Every committee signature is SIGHASH_DEFAULT or fixes the transaction's inputs, so the
    payouts, assert_init, the commits and assert_final cannot gain fees after signing.
  - The assert chain has no output the operator could use for CPFP: assert_init's outputs go only
    to the commits, the commits' outputs only to assert_final, and assert_final's only to A.
  - If fees rise above the graph's rate during a challenge, an honest operator may not get A
    mined before T_assert, and anyone can slash it.
  - The challenge, the slashes and the refunds are not affected: their posters choose the fee
    (their own inputs, output 1, or their own signature).
  - Anchor outputs, or SIGHASH_ALL|ANYONECANPAY fee inputs, belong to M8, with the pinning
    analysis.
- **Data availability.** A watcher decides whether to challenge from (S, π), assumed to be
  published with the graph. A watcher that cannot get π should challenge.
- **The committee checks nothing.** In `tampered` the committee presigned a statement that π does
  not prove, as BitVM2's committee presigns claims it does not verify.
  - In v1 every input to the proof is in the opened sale list, so an honest committee member
    could refuse to sign S′ outright. That is M1's first lesson, still open, and M4's job.
- **The economics hold at one fee rate** (§6).
  - The bond needed grows with the fee rate.
  - A miner can redirect any slash reward.
  - Half the bond as the burn is a choice, not an optimum.
- **Not exercised:**
  - reorgs: §3 is a written policy;
  - pinning;
  - more than one challenger racing for KC.
- **Standardness.** 430 of the 432 disprove leaves still need a miner to include a non-standard
  transaction, as in M1. Every other transaction in the graph is standard.
- **Demo keys and setup.** The committee is one key. Operator, challenger, buyer and seller keys
  are SHA-256 of public labels. The Groth16 setup is M1's insecure deterministic one.
- **Two runs.** `challenged` and `tampered` ran before `sendrawtransaction` gained
  `maxburnamount` (run b in `timings.txt`). Neither sends a burn through that RPC: the tampered
  disprove went in by `generateblock`. The other four scenarios ran with the final binary
  (run c). Each run started a fresh chain.
