# M1: settling a v1 clearing proof on Bitcoin regtest through BitVM

Run 2026-10-31 to 2026-11-01. Everything below was executed and measured. The demo keys
and Groth16 setup are public, so **none of it is safe with real funds**; it is regtest only.

- **Machine:** AMD Ryzen AI 9 365, WSL2 Ubuntu 24.04 with a 20 GB VM, Rust 1.99.1.
- **Groth16:** v1 `accounting16x4_committed`, rebuilt with `groth16/run.sh`. The verifying
  key's sha256 is `3d5030f9fb7c785b5d3d0ce14d958b051293008edde6d6dcabba14b8533494ec`, the
  same as in GROTH16.md.
- **Verifier:** BitVM `c620dbf` (the chunked Groth16 verifier in `bitvm/src/chunk`), plus
  [`patches/0001-bitvm-18-public-inputs.patch`](patches/0001-bitvm-18-public-inputs.patch)
  (+90/−4 lines).
- **Node:** Bitcoin Core v31.1.0 (`bitcoind -regtest`, release tarball checked against
  `SHA256SUMS`), default policy apart from `-blockmaxweight=4000000`.

## Result

| Scenario | What the operator asserts | Outcome on regtest |
|---|---|---|
| honest | the proven signals S and proof π | payout pays exactly the template, 6 blocks after the assert |
| tampered | S′ (50,000 sats of refund moved from buyer 2 to buyer 1) with π | BitVM leaf 431 (final pairing check) disproves; bond slashed; buyers refund |
| mismatch | S and π, but the payout was presigned for S′ | BitVM finds nothing (π is valid for S); binding leaf for `refund[0]` disproves; bond slashed; buyers refund |
| plus-r | S with `refund[1]` written as x + r | BitVM MSM leaf 30 disproves (its `Fr::is_valid` range check); bond slashed; buyers refund |
| stall | nothing | buyers refund after 30 blocks; a refund one block early is rejected |

In every disproved scenario the presigned payout is then rejected (`bad-txns-inputs-missingorspent`).
In the honest one, consensus rejects two disproves a challenger might try (the final pairing leaf
and a binding leaf, each with the honest witness) and the payout one block early.

## Reproduce

All of it runs in WSL2 Ubuntu 24.04 (or any Linux), in a native directory, not `/mnt/*`.

```sh
# 1. Groth16: circuit, insecure deterministic setup, the example proof (groth16/run.sh),
#    then a proof for the regtest batch with the same proving key.
PATH=/root/zkc-tools/node/bin:/root/zkc-tools/bin:$PATH \
  bash research/zk_clearing/bitvm/prove-batch.sh /root/zkc-m1
# 2. BitVM c620dbf plus the patch, the workspace, and its tests.
bash research/zk_clearing/bitvm/scripts/build.sh /root/zkc-m1
# 3. Conversion reports, disprove scripts, a private bitcoind -regtest, and every scenario.
BITCOIN_BIN=/root/opt/bitcoin-31.1/bin bash research/zk_clearing/bitvm/scripts/run-m1.sh /root/zkc-m1
# Script-level checks without a node. --all-plus-r adds the x + r sweep over all 18 signals.
/root/zkc-m1/target/release/zkc-m1 selftest /root/zkc-m1 --all-plus-r
```

[`results/`](results/) holds what these runs wrote:
- the conversion reports;
- the disprove-leaf survey;
- the self-test;
- one trace per scenario, with every txid, vbyte and weight count, mempool verdict and rejection reason;
- the timings.

`cargo test --release` runs 7 conversion tests and 4 template tests.

## 1. Proof conversion (snarkjs → arkworks)

[`convert/`](convert/src/lib.rs) reads `verification_key.json`, `proof.json` and `public.json`
into `ark_groth16::{VerifyingKey, Proof}<Bn254>` and `Vec<Fr>` (arkworks 0.5, the version
BitVM uses).
- `IC` becomes `gamma_abc_g1`, in public-signal order.
- G2 coordinates are read as snarkjs writes them, `[c0, c1]`.

It refuses rather than repairs:
- a non-canonical decimal;
- any field element ≥ its modulus;
- a projective z other than 1;
- a point off the curve or outside the subgroup.

| Check (both the run.sh example proof and the regtest batch proof) | Result |
|---|---|
| Converted proof verifies with `ark_groth16::Groth16::verify_proof` | yes |
| Each of the 18 signals + 1 | 18 of 18 rejected |
| A signal written as x + r | refused at parse time (all 18 positions tested) |
| Proof for one statement against the other's signals | rejected |
| A and C swapped, A negated, two IC points swapped | rejected |
| G2 read as `[c1, c0]` | refused (off the twist) |
| Compressed arkworks proof | 128 bytes; proof and key round-trip |

## 2. BitVM's chunked verifier with 18 public inputs

BitVM `c620dbf` hard-codes one public input (`NUM_PUBS = 1`). The patch makes three changes.

1. **18 public inputs.**
   - `NUM_PUBS = 18`.
   - `NUM_HASH` goes from 363 to 431. Each scalar takes 4 MSM chunks (254 bits at 8 windows of
     8 bits per chunk), so the extra 17 scalars add 68 hashed intermediates.
   - The MSM code was already generic over the number of scalars.
2. **A prover-side panic on the identity point (BitVM bug).**
   - `G1Affine::hinted_check_add_prevent_degenerate` (`bn254/g1.rs:177`) asserts `t != q` and
     `t != -q` before checking for the identity.
   - The MSM accumulator starts at the identity (`bn254/msm.rs:280`), and table row 0 is the
     identity (`msm.rs:128`). So the first addition panics whenever the first 8-bit window of the
     first scalar is zero.
   - Here 4 of the 18 signals are zero, because buyer slot 3 is padding. In BitVM's reversed order
     the first scalar is `buyerId[3] = 0`, and assertion generation panicked.
   - With one public input, by the same code path, any input whose lowest byte is zero would
     panic: 1 value in 256. That case follows from the code; it was not run.
   - The script itself already handles an identity operand in its `is_zero` branches, which push
     no hints. The patch therefore keeps the assertions only when both points are non-identity.
     The honest proof then validates on all 432 chunks.
3. **Additive helpers with no behaviour change:**
   - `api_get_pubkeys`;
   - `api_u256_assertion_bytes`, the assertion encoding of any 256-bit value, needed to commit
     x + r;
   - `api_disprove_witness_for_leaf`, the witness for any leaf, used to show that disprove leaves
     fail on honest data.

BitVM stores public inputs in reverse order (`msm_scalar.reverse()`). Signal i therefore sits at
Winternitz slot 17 − i. The harness checks all 18 assertion encodings against its own encoder
before using them.

**Disprove leaves** (`results/leaves.json`): 432 leaves, 1,289,259,813 bytes in total.
- Size: smallest 338,312 B, median 2,889,666 B, largest 3,948,062 B (leaf 425).
- 430 of the 432 exceed the 400,000-weight standardness limit, so a disprove through them is mined
  directly (`generateblock`), as any miner could.
- The 72 MSM leaves are 2.53–2.62 MB each, 189 MB in all. Going from 1 to 18 inputs added about
  175 MB.

## 3. The transaction graph

```
escrow[b]     buyer funds funding[b]; P2TR, NUMS internal key
                {payout: <committee> CHECKSIG | refund: 30 CSV, <buyer b> CHECKSIG}
bond          operator, 0.1 BTC, key path
assert_init   bond -> K (operator) + 42 commit outputs C_j
commit[k]     C_j inputs, each through its leaf:
                Winternitz checksig of a batch of values, then <operator> CHECKSIG  -> connector D_k
assert_final  K + D_0..D_4 -> A; P2TR, NUMS internal key, 451 leaves (depth 9):
                432 BitVM disprove leaves | 18 binding leaves | payout: 6 CSV, <committee> CHECKSIG
payout        A (payout leaf) + every escrow (committee leaf)
                -> the template's outputs + the bond less the fee back to the operator
disprove      A through one disprove or binding leaf -> challenger (the operator loses the bond)
refund[b]     escrow[b] through its refund leaf, 30 blocks after funding
```

**Committee.** One demo key stands in for BitVM2's n-of-n presigning committee.
- It signs the payout (SIGHASH_DEFAULT over all four inputs) before any assertion exists.
- That is possible because segwit txids exclude witnesses. A's outpoint is fixed by the shape of
  the assert chain, not by the Winternitz data.
- It is assumed to sign nothing else. With one key that is an assumption, not a guarantee.

**Assert.** The operator commits 463 values with one-time Winternitz signatures:
- the 18 public signals and the 14 proof field elements, as 32-byte Wots32;
- 431 intermediate hashes, as 16-byte Wots16.

Each commit leaf verifies its batch's signatures against the operator's keys. A missing or
altered signature makes the assert chain invalid, so the data is on chain before A exists.

**Batching.** Batches are cut at 900 stack items. The largest measured execution peaked at
907 items, against the consensus limit of 1,000.

**Challenger.** It reads the signatures back from the mined commit transactions (`getrawtransaction`,
no off-chain channel) and runs BitVM's `validate_assertions`.

**Binding leaves.** Leaf i holds the 64 message digits of the value the payout template was built
from, and opens iff the operator's commitment to signal i decodes to anything else.
- Without them, an operator could have a payout presigned for one statement S′ and then assert
  another, S, for which π is valid. BitVM would find nothing to disprove (the mismatch scenario).
- Each binding leaf is 10,521 bytes.

## 4. Payout template

[`m1/src/template.rs`](m1/src/template.rs) maps (18 signals, sale-list opening) to outputs:

1. Every signal is below r, and every amount is ≤ MAX_SATS.
2. `saleCommitment` equals Poseidon of the opened sale list, computed by circomlibjs
   (`groth16/commit.js`). `buyerId[b]` equals the opening's buyer IDs.
3. One output per seller payee: active sale slots in order, merged by payee at first appearance.
   The prices must sum to `totalPayout`.
4. `refund[b]` to buyer b's refund payee, for each funded slot.
5. The sum of `feeBudget[b]` to the fee payee.
6. The outputs must sum to the escrowed `funding[b]`, and no output may be below the 330-sat P2TR
   dust limit.

The per-buyer equation `funding[b] = cost[b] + feeBudget[b] + refund[b]` is left to the proof.
That gap is what the tampered statement S′ exploits: it conserves the total but breaks buyer 1's
equation.

Outputs for the regtest batch: Alice 1,900,000; Bob 1,800,000; Carol 450,000; refunds 330,000,
82,000 and 43,000; fee 45,000. Escrows: 2,000,000, 1,900,000 and 750,000. The mined honest payout's
first seven outputs were compared byte for byte with the template and are equal.

## 5. Range checks on public inputs (≥ r)

| Where a public input is consumed | Check | Evidence |
|---|---|---|
| snarkjs → arkworks | parse refuses values ≥ r | 18 of 18 positions, conversion tests |
| Payout template | refuses signals ≥ r | 18 of 18, template tests |
| Commit leaves | verify signatures only; they do not interpret the value | a commitment to x + r is accepted on chain, then disprovable |
| BitVM MSM chunks: 4 per signal, 72 in all | `Fr::is_valid` on the scalar (`chunk/taps_msm.rs:47` for the first chunk, `:81` for the rest). An invalid scalar sets the validity bit to 0, which the hash layer turns into a successful disprove (`chunk/wrap_hasher.rs:255`) | regtest: x + r on `refund[1]` disproved through leaf 30 in a 656,885 vB transaction. Self-test sweep: x + r on each of the 18 signals in turn opens the first MSM chunk of that scalar (leaves 70, 66, …, 6, 2 for signals 0…17), and the challenger's witness executes successfully; 768 s in all |
| Binding leaves (18) | byte-exact comparison with the template value | self-test: each of the 18 opens on x + r and stays shut on the honest value |

Only the first MSM chunk of each signal was executed on x + r. BitVM derives no segments past the
first faulty one, so chunks 2–4 of a signal cannot be handed a witness through its API. They run
the same guard at `taps_msm.rs:81`.

## What M1 does not show

- **The proof adds little in v1.** Every input to the v1 circuit is in the opened sale list or
  the public signals. A committee holding the opening could recompute everything the proof says
  and reject S′ itself.
  - The disprove path starts to matter once the circuit proves facts the committee cannot see:
    seller signatures and sharechain ownership, the "Not bound" rows in GROTH16.md.
  - S′ here has no valid proof at all.
- **Fee budgets are not bound to buyers.** A statement that moves value from a refund to the fee
  keeps every circuit equation, so an operator can prove it honestly. `feeBudget[b]` has to come
  from the buyer's signed escrow terms, through the template or the circuit.
- **Seller payout scripts are not bound.** The template takes them from the opening's payee
  labels, as GROTH16.md says.
- **The committee is one key**, and the operator, challenger, buyer and seller keys are SHA-256
  of public labels. Winternitz secrets come from a public seed per graph, and the Groth16 setup
  is the insecure deterministic one.
- **Simplified BitVM2.**
  - There is no kickoff/challenge transaction, so disprove leaves are open to anyone.
  - Nothing burns part of the bond, so the first challenger, or a miner, takes all of it.
  - An operator who posts `assert_init` and then stops keeps its bond: there is no
    assert-timeout slash. Buyers still refund after 30 blocks.
- **Standardness.** 430 of the 432 disprove leaves need a miner to include a non-standard
  transaction. The assert chain is standard.
- **Not covered:** reorgs, fee bumping, pinning, or the timing between the 6-block challenge
  window and the 30-block refund (phase 3).
