# M3: one public input

Run 2026-11-01. Everything below was executed and measured unless marked *est.* The demo keys and
Groth16 setup are public, so **none of it is safe with real funds**; it is regtest only.

The question: what does BitVM settlement cost when the proof has one public signal, a Poseidon
hash of the clearing statement, instead of the statement's 18 values?

- **Machine:** AMD Ryzen AI 9 365, WSL2 Ubuntu 24.04 with a 20 GB VM, Rust 1.99.1. The same
  machine as [M1.md](M1.md).
- **Groth16:** [`accounting16x4_hashed`](../circuits/accounting16x4_hashed.circom), built with
  `groth16/run.sh` and the same insecure deterministic setup as v1. The verifying key's sha256
  is `3264f6073244ed78cbae996e19ba1e6f308bd5868e1c6d488c0dee530ae009fc`.
- **Verifier:** BitVM `c620dbf` with M1's
  [`patches/0001`](patches/0001-bitvm-18-public-inputs.patch), then
  [`patches/0002-bitvm-1-public-input.patch`](patches/0002-bitvm-1-public-input.patch). Patch 0002
  sets `NUM_PUBS = 1` and `NUM_HASH = 363`, which are upstream's values.
- **Graph and node:** M1's graph, with no kickoff or challenge, on Bitcoin Core v31.1.0. The
  harness is the same binary, built against the patched BitVM.

## Headline

**With one public input the assert chain is 336,528 vB, against M1's 422,650: 86,122 vB less
(−20.4%).** The honest path (assert chain plus payout) is 337,255 vB, against 423,361.

The saving all comes from BitVM's MSM: 68 fewer hashed intermediates, 68 fewer disprove leaves
and 178 MB less leaf data. The other 360 leaves are the same size as M1's.

Prepare's peak memory falls from 13.0 GB to 5.9 GB, and a challenger's run from 13.0 GB to
3.3 GB. The circuit grows by 1,074 constraints.

The roadmap estimated about 68 fewer hashed intermediates and disprove leaves, about 175 MB less
leaf data and 85 fewer Winternitz values (about 18%). All four hold. The assert chain shrinks
more than the value count, by 20.4%. Of the 85 values removed, 17 are public signals signed as
Wots32: 67 digits, or 134 witness items. A hash signed as Wots16 is 35 digits, or 70 items. The
committed witness falls from 34,458 to 27,420 items, which is also −20.4%.

**With M2 (est.).** M3 ran on M1's graph, so this is arithmetic, not a run. In M2's optimistic
graph the assert is posted only after a challenge, so the honest, unchallenged batch is 897 vB
whether there are 18 inputs or 1. On the challenged paths, M3 would take M2's assert chain from
422,607 vB to about 336,485 vB. M2's honest, challenged path would go from 423,708 vB to about
337,600, and its tampered path from 662,428 vB to about 576,300.

## Reproduce

Everything runs in WSL2 Ubuntu 24.04, in a native directory. These runs used `/root/zkc-m3`,
apart from M1's `/root/zkc-m1`, and regtest RPC port 18753.

```sh
# 1. The hashed circuit (run.sh: every negative check), then the regtest batch proof and its
#    statement (batch/statement.json) with the same proving key.
PATH=/root/zkc-tools/node/bin:/root/zkc-tools/bin:$PATH \
  bash research/zk_clearing/bitvm/prove-batch.sh /root/zkc-m3 accounting16x4_hashed
# 2. BitVM c620dbf with patches 0001 and 0002, the workspace, and its tests.
ZKC_PUBS=1 bash research/zk_clearing/bitvm/scripts/build.sh /root/zkc-m3
# 3. Clean disprove scripts and assertions, timed.
/usr/bin/time -f "%e s, %M KiB" /root/zkc-m3/target/release/zkc-m1 prepare /root/zkc-m3
# 4. Conversion reports, a private bitcoind -regtest, every scenario.
ZKC_RPC_PORT=18753 BITCOIN_BIN=/root/opt/bitcoin-31.1/bin \
  bash research/zk_clearing/bitvm/scripts/run-m1.sh /root/zkc-m3
# 5. Script-level checks without a node, including the x + r sweep (one signal).
/root/zkc-m3/target/release/zkc-m1 selftest /root/zkc-m3 --all-plus-r
```

[`results/m3/`](results/m3/) holds what these runs wrote:
- the hashed circuit's `run.sh` results;
- the conversion reports;
- the disprove-leaf survey;
- the self-test;
- one trace per scenario, with every txid, vbyte and weight count, mempool verdict and rejection
  reason;
- the timings.

`cargo test --release` runs 11 conversion tests (7 v1, 4 hashed) and 6 template tests.

## 1. The circuit

`accounting16x4_hashed` proves v1's relation, unchanged. The 18 values that were public become
private. The only public signal is

```
statement     = [saleCommitment, funding[0..3], feeBudget[0..3], refund[0..3], totalPayout, buyerId[0..3]]
statementHash = Poseidon2(Poseidon9(statement[0..8]), Poseidon9(statement[9..17]))
```

`statement` is in v1's public-signal order. circomlib's Poseidon takes at most 16 inputs, so 18
values need two levels. Two 9-input hashes under a 2-input one keep every arity within
light-poseidon's limit of 12, so the Rust template computes the same function with circomlib's
parameters.

v1's template moved to [`circuits/committed.circom`](../circuits/committed.circom), so both
circuits include it. v1 still compiles to the same R1CS, byte for byte (sha256 `9428060d…cc795`).

| Check (`run.sh`) | Result |
|---|---|
| Constraints / private inputs / public outputs | 10,078 / 170 / 1 |
| Invalid witnesses (the 17 v1 fixtures) | all 17 rejected by the witness calculator |
| Valid proof | verifies; `statementHash` equals circomlibjs's (`groth16/statement.js`) |
| Re-split sale list with the same totals | proves a different `statementHash` |
| Tampered public signal, signal + r, forged witness | rejected, rejected by snarkjs, rejected |

The regtest batch is M1's, built from the same `input.json`. Its statement equals M1's 18 public
signals value for value, and its hash is
`11965087376643176893676794780256689458608630063703480212075444774827329732333`.

**Conversion** ([`convert/tests/hashed_vectors.rs`](convert/tests/hashed_vectors.rs)):
- both hashed proofs verify under ark-groth16 with one public input (`gamma_abc_g1` of length 2);
- the hash + 1, and each proof's hash against the other proof, fail;
- hash + r is refused at parse time.

## 2. BitVM with one public input

Patch 0002 changes two constants on top of 0001: `NUM_PUBS` goes from 18 to 1 and `NUM_HASH` from
431 to 363. Everything else in 0001 stays:
- the guard on the identity-point panic in `bn254/g1.rs`;
- the three additive helpers.

The harness reads `NUM_PUBS` from BitVM. With 1 it:
- asserts `statementHash` at Winternitz slot 0;
- builds one binding leaf;
- re-encodes `statementHash` as x + r in the plus-r scenario;
- reads the statement from `batch/statement.json` and checks that it hashes to the proof's signal.

The identity-point guard still matters with one input. M1.md traces the panic to a zero first
window of the first scalar, which here would be 1 hash in 256. The batch hash's lowest byte is
237 and the example's is 205, so these runs do not exercise that case.

**Disprove leaves** ([`results/m3/leaves.json`](results/m3/leaves.json)):
- 364 leaves, 1,110,838,527 bytes in all.
- Smallest 338,312 B, median 2,889,666 B, largest 3,948,062 B (leaf 357, the same script as M1's
  leaf 425).
- Leaves 0–1 and 6–363 match M1's leaves 0–1 and 74–431 in size, 1,100,435,879 bytes each way.
  The whole difference is the MSM: leaves 2–5 here, against 2–73 in M1. Each scalar after the
  first costs 4 MSM leaves of 2.53–2.62 MB, about 10.5 MB per public input.

| Step | M1 | M3 |
|---|---|---|
| Partial disprove scripts (depend on the verifying key only; cached) | 309 s | 192 s |
| Honest assertions (generated and checked by executing every leaf) | 223 s | 230 s |
| Tampered assertions | 329 s | 260 s |
| Clean `prepare` in all: time / peak RSS | 869 s / 13.0 GB | 689 s / 5.9 GB |
| Challenger check of an honest assertion (every leaf) | 329 s | 222 s |
| Challenger check in the tampered, mismatch and plus-r runs | 131–156 s | 118–137 s; 3 s for plus-r |

| `selftest --all-plus-r` | 767 s, 13.0 GB (18 signals) | 62 s, 2.9 GB (1 signal) |

The peak RSS figures are the comparison to rely on. The times were taken under different
background load: during the M3 runs another session's snarkjs job ran in the same VM, and the host
was short of free memory. Assertion generation is dominated by the pairing segments, not the MSM,
so it barely moves.

## 3. The payout template checks the preimage

[`m1/src/template.rs`](m1/src/template.rs) adds `statement_hash` and `build_hashed`. The committee
gets the 18-value statement from the operator, alongside the sale-list opening. Given
(`statementHash`, statement, opening), `build_hashed`:

1. refuses a `statementHash` ≥ r;
2. refuses any statement value ≥ r. Reduced mod r, x + r would hash the same as x, so this check
   is what stops a second encoding of one statement;
3. recomputes Poseidon2(Poseidon9, Poseidon9) with light-poseidon 0.3.0 (circomlib parameters,
   arkworks 0.5) and requires it to equal `statementHash`;
4. builds exactly M1's template from the statement, with every M1 check.

Unit tests:
- light-poseidon reproduces the circuit's `statementHash` for the batch statement;
- `build_hashed` on the honest hash and statement returns M1's template, output for output;
- S′ against the honest hash is refused ("does not hash");
- S′ under its own hash builds a different template;
- the hash + r, and each of the 18 statement values + r, are refused.

In every regtest scenario, the first seven outputs of the mined payout were compared byte for byte
with the template and are equal.

One binding leaf now covers the whole statement. It opens unless the operator's Winternitz
commitment to signal 0 decodes to exactly H(S_template). Poseidon is collision-resistant, so a
commitment that keeps the leaf shut fixes every output of the template. M1 needed 18 leaves for
the same effect.

**Data availability.** In M1 the 18 values were readable from the assert transactions. In M3 only
their hash is on chain, so the committee needs the statement from the operator before presigning.
A challenger needs only what is on chain: BitVM's validation and the binding leaf both work on the
committed hash.

The assert chain costs the operator 673,034 sats at 2 sat/vB (the bond minus A's value in the
tampered run), against M1's 845,346.

**The payout's extra 16 vB is tree shape.** The A tree pairs leaves left to right and promotes an
odd node unchanged. In M1's 451-leaf tree the payout leaf was promoted twice and has a 4-hash
Merkle path; in M3's 366-leaf tree it has 6. Two 32-byte hashes are 16 vB. The disproves through
leaf 363 and the binding leaf are lighter for the same reason. Putting the payout leaf near the
root would save the same bytes in either graph.

Honest-run timeline:
- escrows funded at heights 201–203, bond at 204;
- assert_init at 205;
- all four commits in one block at 206;
- assert_final at 207;
- the payout was rejected at tip 207 (`non-BIP68-final`) and mined at 213.

## 5. Range checks on the public input (≥ r)

| Where | Check | Evidence |
|---|---|---|
| snarkjs → arkworks | parse refuses values ≥ r | `statementHash + r` refused (conversion tests, conversion report) |
| Payout template | refuses `statementHash` ≥ r and each statement value ≥ r | template tests: the hash and all 18 statement positions |
| BitVM MSM chunks (4, leaves 2–5) | `Fr::is_valid` on the scalar | regtest: x + r disproved through leaf 2 (633,482 vB). Self-test: x + r on `statementHash` opens leaf 2, and the challenger's witness executes successfully |
| Binding leaf | byte-exact comparison with the template's hash | self-test: shut on the honest hash, open on x + r and on H(S′) |

The statement values never appear on chain, so no script range-checks them. Inside the circuit
they are field elements, and outside it the template refuses non-canonical encodings.

## What M3 does not show

- **The proof still adds little.** One public input does not change M1's first lesson. The
  statement is still recomputable by a committee holding the opening. `feeBudget` and the seller
  payout scripts are still unbound (M4).
- **M3 ran on M1's graph.** The M2 figures above are arithmetic on two runs, not a run of the
  combined graph.
- **The identity-point case** with one input (a hash with a zero first window) was not run; the
  batch and example hashes do not hit it.
- **Merging with M2.** M2's crate compiles `m1/src/template.rs` by path. That file now uses
  light-poseidon, so `m2/Cargo.toml` needs the same dependency when the branches meet.
- Everything M1.md lists as not covered still applies: one committee key, public demo keys and
  setup, 362 of 364 disprove leaves needing a miner to include a non-standard transaction, and no
  fee bumping or pinning analysis.
