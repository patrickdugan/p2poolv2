# M8: toward real value, for the one mode M7 kept

M7 ([../benchmark/BENCHMARK.md](../benchmark/BENCHMARK.md)) narrowed the BitVM path to
**periodic (about daily) settlement of large batches when on-chain fees are low**. In that
mode it costs less per sale than Lightning and locks far less capital. M8 covers only what
that mode needs before real funds.

Run 2026-11-01 on Bitcoin Core 31.1 (regtest) and snarkjs 0.7.5, in WSL2 Ubuntu 24.04.

## Done and verified

### 1. A multi-party phase-2 setup

[`ceremony.sh`](ceremony.sh) replaces the insecure deterministic setup:

- Groth16 setup from a phase-1 file.
- **K contributions**, each with 64 bytes from `/dev/urandom`. In a real ceremony every
  contributor runs this step on their own machine and passes the key on; the result is sound if
  any one contributor destroyed their randomness.
- A **final public beacon**, for example a Bitcoin block hash fixed in advance.
- `snarkjs zkey verify` over the whole chain, then the contribution hashes printed, so each
  contributor can check their own.

Test run on the v1 circuit (`accounting16x4_committed`), with three contributors and the local
phase-1 file standing in for a public one ([results/ceremony-verify.txt](results/ceremony-verify.txt)):

| Check | Result |
|---|---|
| `zkey verify` (3 contributions + beacon against the r1cs and phase 1) | `ZKey Ok!` |
| A proof made with the ceremony key | verifies |
| A proof made with the old insecure single-beacon key, checked against the ceremony's verifying key | rejected (`Invalid proof`): the keys are independent |
| Time and memory | 143 s, 644 MiB |
| Verifying key sha256 | `5470307b…c46f2486` (differs on every run, because the entropy is random) |

### 2. Fee bumping and pinning for the presigned graph

**The problem.** BitVM2 presigns the payout, timeout and disprove spends long before they are
broadcast, so their fees cannot track the market. M2's graph pays a fixed 2 sat/vB, and M2
found the sharp edge ([../bitvm/M2.md](../bitvm/M2.md)): the assert chain has no output a child
could spend for CPFP. If fees spike after a challenge, an honest operator's assert can miss
`T_assert` and the operator is slashed.

**The fix to adopt.** Make every presigned transaction TRUC (version 3), pay zero fee, and give
it a zero-value pay-to-anchor (P2A) output. Whoever needs it confirmed pays through a child.

[`anchor_bump.py`](anchor_bump.py) checks this on a private regtest node
([results/anchor_bump.json](results/anchor_bump.json)):

| Step | Result |
|---|---|
| Zero-fee v3 parent (124 vB, payee + 0-sat P2A), submitted alone | rejected: `min relay fee not met, 0 < 13` |
| Parent + v3 child spending the anchor (153 vB, 1,000 sats) via `submitpackage` | `success`; both in the mempool |
| A second party's child spending the same anchor at 5,000 sats | replaces the low-fee child (TRUC sibling eviction) |
| Next block | contains the parent and the high-fee child |

What this means for the graph:

- **Cost.** Each presigned transaction gets 13 vB larger (the anchor output). A child (about
  150 vB) is paid only when fees have moved.
- **Pinning.** A low-fee child cannot pin the parent, because any party can outbid it with a
  sibling.
- **The limits that come with it:** a TRUC parent may have one child, and a TRUC child is capped
  at 1,000 vB.
  - The payout and the refunds fit easily.
  - 430 of the 432 disprove transactions are above the standardness limit anyway, so relay rules
    don't apply to them (next section).
- **Why it matters.** Two liveness risks are closed by the same anchors:
  - an operator's assert has to confirm before `T_assert`;
  - a challenger's disprove has to confirm before the payout's 6-block window closes.
**Every transaction in M2's graph.** Who can change its fee after presigning, and what to add:

| Transaction | Fee fixed at presign? | Plan | Pinning |
|---|---|---|---|
| kickoff, refunds, escrow/bond/reserve funding | no: signed when broadcast | none needed | — |
| challenge | no: `SINGLE\|ANYONECANPAY`, the challenger adds inputs and change | none needed | rival challenges all destroy KC, so any one is enough |
| disprove, timeout | no: `SINGLE` fixes only the burn; the poster sets the rest of the bond's output, fee included | none needed. The fee comes out of the challenger's reward, which is M2's bond-scaling bound below | a miner can take the reward; the burn is fixed |
| payout_unchallenged, payout_asserted | **yes** (`DEFAULT` over every input and output) | TRUC v3, zero fee, 0-sat P2A anchor, as tested above | none: TRUC sibling eviction |
| assert_init, commit[k], assert_final | **yes**: their txids are fixed so the committee can presign over them | an anchor on each, **keyed to the operator** | commits are 53–92 kvB, over TRUC's 10 kvB cap, so they cannot be v3. A keyless anchor on a non-TRUC transaction lets anyone attach a large low-fee child and pin it. A keyed anchor leaves CPFP to the operator alone |

- **Still to do.** Adding these anchors to M2's graph is the follow-up implementation. This
  check shows the mechanism on Core 31.1, not the full graph.
- **The bond, from M2.** A slash pays the challenger half the bond less fees, 4.52 M sats from
  0.1 BTC. M2 estimates that covers a largest-leaf disprove only up to about 3.5 sat/vB. So
  the bond has to be set from the highest fee rate the settlement mode accepts.
- **Posting a slash.** The slash's burn output carries value, and `sendrawtransaction` refuses
  it unless the caller passes `maxburnamount` of at least the burned amount.

## Specified, not built

### 3. Non-standard disprove transactions

- **The issue.** 430 of the 432 disprove leaves produce transactions above 400,000 weight
  units, so the public P2P network will not relay them.
- **What does not work:** a pool node's ordinary `getblocktemplate` includes only mempool
  transactions, and on mainnet Bitcoin Core does not accept non-standard transactions into its
  mempool at all.
- **The routes, in order of preference:**
  1. **Shrink the leaves.** M3 cuts 68 leaves; BitVM's chunker can target a smaller per-leaf
     script size at the cost of more leaves and a longer assert. Measure what fits under the
     400 k WU limit.
  2. **Submit straight to a miner.** P2Poolv2 is itself a set of miners, so a challenger can
     hand the disprove to any participating node operator. That operator can add it to a block
     template they build and submit (`submitblock`), without the mempool.
  3. **Fall back** to relays that accept non-standard transactions.
- **What must hold.** Each route has to land a disprove within the 6-block challenge window, and
  this is to be tested on signet before any value.

### 4. A real n-of-n committee

- **What replaces the single demo key:** n independent signers (MuSig2, BIP327), who presign
  each batch's payout, timeouts and disprove paths before the escrows are funded.
- **The assumption.** The graph is safe if one signer is honest and deletes their key after
  presigning, the standard BitVM2 assumption. Liveness needs every signer online for presigning.
- **Who:** the market makers plus at least one party independent of them, for example a
  P2Poolv2 node operator chosen by the pool.
- **Not done.** It needs real, separate signers.

### 5. Signet trial

The plan:

1. Run one P2Poolv2 node and bitcoind on signet.
2. Fund escrows and the operator bond from a signet faucet.
3. Settle one daily batch through the M2 graph with TRUC anchors.
4. Run one deliberate challenge and disprove through route 2 above.

**Pass condition:** every scenario in M2 behaves the same on signet, and the disprove confirms
inside the challenge window.
